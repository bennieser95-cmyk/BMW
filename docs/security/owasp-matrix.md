## Evidenzbasierter Workflow-Fund

**S1 – Produktionsmigration mit unbegrenztem Tag-Trigger:** ein
`v*.*.*`-Tag startete zuvor eine Migration mit produktiven Zugangsdaten, bevor
die manuelle `production`-Freigabe des Promote-Jobs griff. Damit konnte ein
nicht autorisierter Tag-Code mit Produktionssecrets ausgeführt werden
(A08; Confidence 8/10). Der Release-Deploy-Job ist inzwischen ebenfalls an das
GitHub Environment `production` gebunden. **Die technische Mitigation ist
erst wirksam, wenn GitHub Required Reviewers/Self-Review-Sperre und das
geschützte Tag-Ruleset tatsächlich konfiguriert sind.** Bis dahin bleibt der
Befund operativ offen; keine Produktionstags erstellen.

S1–S4-Klassifizierung gemäß Dok. 06: S1 kritisch (Ausfall, Datenverlust oder
Sicherheitslücke), S2 hoch (Kernfunktion ohne Workaround eingeschränkt), S3
mittel (Einschränkung mit Workaround), S4 niedrig (kosmetisch/geringe
Auswirkung). Im Anwendungscode wurden keine weiteren ausnutzbaren Findings
bestätigt; der unten dokumentierte Dependency-Befund ist separat zu bewerten.
Die oben als offen/nicht prüfbar markierten Bereiche sind Nachweis-Lücken und
müssen vor Go-Live geschlossen werden.

## Offener Dependency-Befund

**S1 – Kritische Better-Auth-Advisories im Neon-Auth-Abhängigkeitsbaum:**
`npm audit --audit-level=high` meldet `better-auth` als kritisch und
`@neondatabase/auth` als direkt betroffene High-Abhängigkeit. Die Advisories
benennen unter anderem mögliche Anmeldung als fremder Nutzer über den
OAuth-Proxy bzw. OAuth-State sowie eine Ressourcenerschöpfung in einer
verschachtelten Zod-Version. Ob die betroffenen Pfade in der konkreten
Neon-Auth-Beta-Konfiguration erreichbar sind, ist nicht geprüft. Owner:
Auth-/Backend-Agent (Agents 2–4). Keine automatische `npm audit fix --force`
ausführen; vor Produktionsfreigabe eine kompatible, gepinnte Behebung oder
nachweisbare Mitigation plus vollständige Auth-E2E-Suite erforderlich.
